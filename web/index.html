Scale

100× the load.The same cost per marker.

From 1,000 to 10,000,000 markers, 100 runs at each size. Geometry time grows in step with the count, 48 to 80 ns per marker at every size. The physics layout grows faster; one layout of 100,000 markers took 13.6 min, so we stopped there.

Quality

Position keeps its meaning.Physics scatters time.

Speed matters only if the picture is right. For every finished layout we checked two things: is each marker inside its own band, and do markers that follow each other in time run the same way around the globe. 3apart gets both right by construction. Physics keeps most markers near their band, but its time order is a coin flip.

The physics forces were tuned for this task: a pull onto the sphere and a pull toward the middle of each marker's band. With d3's default strengths, 74% of markers ended up outside their band in a trial at 1,000 markers. The band pull also gathers markers on the band's middle line, so the value that 3apart shows as height inside the band is lost.

Method

How we measured.

What was measured

Each marker has a band (one of 24), a time and a value, drawn from a fixed random seed. Synthetic data only.

3apart geometry is the disclosure's place and sphere_xyz: band edges with a 0.9 cap, a 12% margin inside each band, longitude from time. The NumPy re-check runs the reference code unchanged. The JavaScript and GPU versions are line-for-line ports.

"Time to a finished layout" is one placement for geometry, and building the simulation plus d3's standard 300 ticks for physics. Each size ran 100 times except the physics layouts: 100 at 1,000 markers, 10 at 10,000 markers, 1 at 100,000 markers.

The physics layout

d3-force-3d 3.0.6, the library behind most 3D force graphs. Many-body repulsion with the Barnes–Hut approximation (theta 0.9), links between markers that follow each other in time within a band, a radial force that holds markers on the sphere, and a pull toward each marker's band. It starts from random points on the sphere and runs alpha from 1 to 0.001 over 300 ticks.

The forces were tuned for band membership (charge −10, radial and band pulls at full strength), so the comparison is against the physics layout at its best for this task. A new marker is added with one link to its band and the layout is reheated to alpha 0.3 and run until it settles, about 248 ticks.

The GPU code

WebGL2 with float textures. Geometry is one fragment-shader pass that writes every marker's position. Physics is one pass per tick that updates position and velocity together: all pairs up to 16,384 markers; above that, each marker feels a random sample of 1,024 others, scaled up to the full count. Links, the radial pull and the band pull are the same as on the CPU; all markers update at once from the previous tick.

Times are wall-clock from the draw call to a one-pixel read-back, so they include the round trip to the GPU. Where the browser offers GPU timer queries, those are recorded too. The emulated numbers come from SwiftShader, which runs the GPU's work on this server's 2 CPU cores: they show the shaders run and agree with the CPU formula, not how fast a GPU is.

What this does not show

A force-directed layout encodes graph relations, and 3apart geometry encodes fixed bands. The disclosure calls this a design choice rather than an equal-task speed claim, and that still holds: these numbers compare two ways to lay out a banded globe, not two solvers for the same problem.

On the GPU, physics compares all pairs up to 16,384 markers, which is more work per tick than Barnes–Hut. A tuned GPU force layout with a tree or a grid could run each tick several times faster, but it would still need about 300 ticks to settle.

CPU numbers come from one core of one server; a laptop will differ, which is why the page can run on your machine. The 100,000-marker physics layout ran once, because one layout takes 13.6 min. Sizes above 100,000 were not run for physics on the CPU.
